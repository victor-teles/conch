## Doc inconsistencies, settled against the 0.22.0 `.d.ts`

1. **`text` vs `content`.** `@json-render/react` 0.22.0 ships no `Text`/`Heading` component, and its `.d.ts` defines no text-prop convention. A component's props are whatever our catalog zod declares (`InferComponentProps<C, K>`), and the generated prompt describes the same zod. The `content` in the AG-UI example belongs to that example's own catalog. Our contract stands: **`text`** (`Heading`, `Note`).
2. **`statePath`/`valuePath` vs `$state`.**
   - `valuePath` appears nowhere in the core or react `.d.ts` files or the react README (0 matches).
   - Reads use `{ "$state": "/path" }`. Two-way binding uses `{ "$bindState": "/path" }`, which the renderer exposes as `bindings[prop]` and which you consume with `useBoundProp`. `useStateBinding(path)` still exists but is marked `@deprecated`.
   - `statePath` survives in two places only: `UIElement.repeat: { statePath: string | { $item: string }; key?: string }`, and the **param name** of the built-in actions (`setState { statePath, value }`, `pushState { statePath, value, clearStatePath? }`, `removeState { statePath, index }`, `validateForm { statePath? }`).
3. **The two `setState` forms.** Both are real, at different layers:
   - Registry action handlers, the ones we would write, get the **updater** form: `ActionFn<C, K> = (params: InferActionParams<C, K> | undefined, setState: SetState, state: StateModel) => Promise<void>`, with `SetState = (updater: (prev: Record<string, unknown>) => Record<string, unknown>) => void`. If the getter passed to `handlers(getSetState, getState)` returns `undefined`, the handler gets a no-op setter (0.21.2).
   - The **path** form `setState: (path: string, value: unknown) => void` belongs to core's `ActionExecutionContext`, used by core `executeAction` and custom renderer bridges. It matches `StateStore.set(path, value)`.
   - `"setState"` is also a built-in **action name** used in specs (`{ "action": "setState", "params": { "statePath", "value" } }`). `ActionProvider` executes it with no handler.
   - Our `run_action` should write through our own store (`store.set`), not through either setter.

## Other findings that matter for Phase 1

- `catalog.prompt()`'s default rules tell the model to "ALWAYS include a state field with realistic sample data". That is the opposite of our no-literal-data rule (lesson 1). Generate the prompt ourselves from our catalog; do not use the library default.
- Because of S5(b) and S8, json-render validates less than our zod. `catalog.validate` also strips `on` and `watch` from its output. The bun-boundary `PanelSpec`/`MiniApp` zod remains the only real gate on either branch.

## Decision

**Recommended branch: in-house** (Step 3.2b). The decision rule requires S1, S2, S3, S4, S5, S6, S7, S8 and S10 all to pass, and **S8 fails**. With 0.22.0, bad params reach the action handler, and an unknown action name passes both `catalog.validate` and `validateSpec`.

Everything else passed: release age, React 19 / StrictMode, one zod, bundle cost (+0.5 KB main, 21.3 KB lazy), compile-time exhaustiveness, store-scoped re-renders, `$state`/`visible`, stable keys with exit animations. If you would rather take json-render with an adapter-enforced S8, the plan's rule does not cover that. The adapter would emit `on` only from zod-validated `ActionButton.props.action` and parse `run_action` params with `RunActionParams`. That makes json-render a working renderer, but we would still own the prompt (default rules conflict), all validation (S5 gaps, stripped `on`), the visible error boundary, and the fact that built-in store-writing actions are reachable from any `on`. Against the planned ~300-line walker, store and `visible` evaluator, that is little gain for a fast-moving 0.x dependency.

**Version to pin: none** on the recommended in-house branch. If you choose json-render anyway, pin **`@json-render/core@0.22.0` and `@json-render/react@0.22.0` exactly** (`bun add -E`). It is the newest release at least 14 days old, its code is identical to 0.21.4, and its `.d.ts` is identical to the current 0.23.2.
